# coCN

coCN 是一门以中文关键字编程的通用语言。它自带三条执行通道——树遍历解释器、
字节码虚拟机、直接机器码后端——并且**解释器与编译器本身都用 coCN 写**（自举）。

```co
输出("你好，世界")

函数 斐波那契(整数 n) -> 整数
    如果 n < 2 则
        返回 n
    结束
    返回 斐波那契(n - 1) + 斐波那契(n - 2)
结束

输出(斐波那契(10))
```

## 安装

```sh
npm install -g cocnlang          # 短名包（推荐）
# 或 npm install -g @yeyelailou/cocn
```

装完即用，不需要额外下载或编译：

```sh
cocn 你好.co
```

要求 Node.js 18+；npm 会按当前平台自动安装对应的平台子包
（`linux-x64` / `linux-arm64`，含预置的引导器二进制）。

## 命令行

| 命令 | 作用 |
|------|------|
| `cocn 程序.co [参数...]` | 运行程序（默认优先走原生快路径） |
| `cocn --编译 程序.co 输出` | 用直接机器码后端编成静态 ELF（x86-64，不依赖 gcc） |
| `cocn --检查 程序.co` | 能力自检：这个程序能否走原生快路径，不能则给出原因 |
| `cocn --生成C 程序.co 输出.c` | 导出中间产物（调试/教学用） |
| `cocn` | 进入 REPL |

### 三条执行通道

| 通道 | 实现 | 说明 |
|------|------|------|
| `native` | 直接机器码 ELF | 最快；目前只有 x86-64 目标 |
| `vm` | 字节码虚拟机（coCN 写） | 回退通道，语义真值由解释器保证 |
| `eval` | 树遍历解释器（coCN 写） | 回退通道，最接近源码语义 |

用环境变量指定：`COCN_BACKEND=eval cocn 程序.co`。
`native` 编译不了的写法（如当前未支持的原生字典/浮点）会自动回退到解释器，
结果正确、只是慢；用 `cocn --检查` 可以提前知道会走哪条路。

## 性能（同机同架构实测）

| 场景 | coCN | C | Rust | 说明 |
|------|------|---|------|------|
| x86-64 直接机器码 | 0.81 ms | 0.66 ms | 0.70 ms | 同档，差 20~25% |
| aarch64 引导器 | 81 ms | 14.9 ms | 16.3 ms | 回退到宿主 C 解释器，差约 5.5× |

差距的根因不是解释器慢，而是**直接机器码后端目前只产出 x86-64 ELF**：
非 x86 平台走不到快路径，只能用引导器。补齐 aarch64 目标是下一阶段的主要工作。
自举解释器（`eval`/`vm` 通道）在 0.1.39 中提速 1.5~9.7×，细节见下文「开发准则」。

## 已知限制

- 直接机器码后端目前只支持 x86-64；aarch64 平台回退到引导器。
- 原生后端暂不支持字典与浮点（会自动回退解释器，结果正确）。
- 并发、网络、部分系统调用的语义以解释器为准，原生通道可能回退。

## 一、项目定位

coCN 是一门**用 coCN 自身编写的中文编程语言**：词法分析、语法分析、求值器、字节码虚拟机、标准库、包管理器与原生编译器均由 `.co` 源码构成。目标是对标 Rust 的现代工程成果，但保留中文关键字与中文标准库的表达方式。

既定方向：

- **T1 已交付**：生态、包管理器、注册表、CI、发布治理。
- **T2 排期 0.2–0.5.x**：async/await、trait 式泛型、过程宏等编译器级特性。
- **T3 明确排除**：不照搬 Rust 借用检查；以运行期语义正确性和三通道一致为红线。
- **唯一硬红线**：native / eval / vm 三通道对同一程序必须输出**逐字节一致**；宿主 C 启动器是语义真值参照。
- **诚实边界**：原生后端只覆盖可安全直译的子集；不支持浮点、字典、类、并发等写法时自动回退解释器。宁可回退，也不生成结果错误的 ELF。

### 当前能力

- 通用编程：OOP、静态类型标注、模块、模式匹配、推导式、真并发、异步 Promise、生成器、迭代器、内置 HTTP/JSON、枚举、装饰器、命名空间、文件 IO。
- 系统编程：完整位运算、进制字面量、字节级视图。
- 三通道：宿主 C 启动器、eval 树遍历、vm 字节码虚拟机；`cocn 程序.co` 默认走原生直译缓存。
- 工具链：对标 Cargo 的 15 条 `cocn` 子命令、`co.toml`、crates.io 式注册表、注册表回退导入。
- 当前首批包：**19 个**，全部完成三通道验证。

### 0.1.39 变更摘要（本版，自解释器大幅提速）

性能（自解释器 eval / vm 通道，同机交替 A/B、各取两轮最小值，基准 fib(22)）：

| 通道 | 改前 | 改后 | 变化 |
|------|------|------|------|
| eval | 42148 / 42525 ms | 39869 / 38108 ms | **快 5.4% / 10.4%** |
| vm | 35703 / 37130 ms | 33241 / 29933 ms | **快 6.9% / 19.4%** |

三处优化（都不改语义，只减工作量）：

1. **VM 分派链热操作码前置**：`v_执行` 原本是 66 长的线性 if/else 链，
   而每轮循环都要用到的 `OP_循环条件` 排在第 39 位 —— 每条指令先做 38 次
   无效比较。改为把热操作码（加载常量/加载局部/存储局部/二元/跳转/
   跳转若假/循环条件/调用/返回…）按频次排到链首，冷门操作码留在后面。
2. **求值器合并异常/控制判定**：`执行块` 里原本写「是异常(r) 或 是控制(r)」，
   两者判定后走的分支完全相同（都直接 return r），却各付一次函数调用 +
   一次 `类型()` + 一次 `包含()`。合并成 `是异常或控制()` 后，
   每条语句少一次函数调用与一次类型判定。
3. **赋值路径三次作用域链合并为一次**：原来「取旧值 → 查类型标注 → 写新值」
   各自独立走一遍作用域链（`查找变量` / `查标注` / `赋值变量`），
   循环体里赋值是最高频操作。合并成 `赋值标识符()`：一次遍历同时完成
   取旧值、函数名不可覆盖判定、类型标注复查、写回（判定条件与原来逐条一致）。

安装与分发：

- **短名包** `cocnlang`（无作用域，几 KB 薄壳，依赖 `@yeyelailou/cocn`）：
  `npm install -g cocnlang` —— 与 deno/bun/python 同款短命令。
  （npm 以「包名与既有包过于相似」为由拒绝了 `cocn` 与 `cocn-cli`，
  `cocnlang` 可用；`cocn-zh-lang` 已 deprecate，只保留一个主短名。）
  薄壳是 sh 脚本：Android/Termux 没有 `/usr/bin/env`，shebang 写
  `#!/usr/bin/env node` 的全局命令会直接不可执行。
- **一键脚本** `install.sh`（不装 npm 也能用）：
  `curl -fsSL https://gitee.com/COSMOnb666/coCN/raw/main/install.sh | sh`
- 入口分家：`bin/cocn.js`（sh 薄壳，给 npm bin 链接用）与 `bin/入口.js`
  （纯 JS 逻辑，给 node 直接调用用）。

平台识别：

- 加 `.gitattributes`，把 `.co` 标为可识别文本并排除构建产物。
- 备好 Linguist 语言定义 `工具/发布/linguist/languages.yml`，
  给 github/linguist 提 PR 即可让 Gitee/GitHub 认得 coCN（只需 GitHub 账号）。

## 四、运行环境

当前开发机：Termux / Android aarch64，Node.js v24.18.0。

关键限制：

- `/storage/emulated/0` 是 **noexec**。直接在该分区执行编译产物会 `Permission denied`；跑门禁前把仓库复制到 `$HOME`，或只执行 `node`/`bash` 脚本。
- `/tmp` 不可写。统一使用：

```bash
export TMPDIR=$HOME/cocnwork/tmp
mkdir -p "$TMPDIR"
```

- 仓库自带的 `bin/引导器` 是 **x86-64 ELF**，aarch64 本机不能直接执行。需要本机跑三通道时，
  用仓库内的宿主 C 源码 `工具/引导器/co.c` 编译 aarch64 引导器（产物放 `$HOME`，不进仓库）：

```bash
aarch64-linux-android-clang -O2 -pthread -o "$HOME/cocnwork/引导器-arm2" 工具/引导器/co.c -lm
```

  引导器源码是语义真值参照，必须随仓库一起演进；过去只留二进制、源码放在远端历史，
  会让「本机重编译」多一步且容易失配，现已收回仓库。

  编译后用 `COCN_BOOTSTRAP` 指定它（`bin/cocn.js` 与 `工具/生态/验证三通道.js` 都已支持该环境变量）：

```bash
export TMPDIR=$HOME/cocnwork/tmp
export COCN_BOOTSTRAP=$HOME/cocnwork/引导器-arm2
COCN_VERIFY_TIMEOUT=300000 node 工具/生态/验证三通道.js
```

  注意：仓库自身的 `bin/引导器` 保持 x86-64 原样，不要用 aarch64 产物覆盖它（那是发版给用户用的预置二进制）。

- 原生启动器 `bin/cocn` 由 `工具/原生编译器/启动器.c` 编译；ABI 与版本相关：

```bash
aarch64-linux-android-clang -O2 \
  -DCOCN_ABI='"cocn-direct-0.1.25"' \
  工具/原生编译器/启动器.c -o bin/cocn
```

  注：直编译后端只产出 x86-64 ELF，aarch64 上 native 通道实际走 `bin/cocn.js` → 引导器自解释器路径；`COCN_BOOTSTRAP` 指定 aarch64 引导器后，native 通道输出与 eval/vm 仍逐字节一致。

- 慢速宿主上，三通道验证单通道默认 60s，可能误判超时：

```bash
COCN_VERIFY_TIMEOUT=180000 node 工具/生态/验证三通道.js
```

## 五、常用命令

### 运行程序

```bash
cocn 程序.co

```

```bash

```

### 能力自检：能否走原生快路径

```bash
cocn --检查 程序.co
```

原生后端不支持的写法（浮点、字典、真除法……）会**静默回退**到解释器通道：
结果依然正确，但速度掉一个量级。这个命令把回退原因与改写建议直接说出来
（可原生 → 退出码 0；需回退 → 退出码 1）。

### 语言套件三通道

```bash
cd /storage/emulated/0/MT2/apks/coCN
bash 测试/套件三通道.sh
```

### 全部示例包三通道

```bash
cd /storage/emulated/0/MT2/apks/coCN
export TMPDIR=$HOME/cocnwork/tmp
COCN_VERIFY_TIMEOUT=180000 node 工具/生态/验证三通道.js
```

### 单个包三通道

```bash
ROOT=/storage/emulated/0/MT2/apks/coCN
PKG=$ROOT/示例包/<包名>
export TMPDIR=$HOME/cocnwork/tmp

# native
cd "$PKG"
PWD="$PKG" node "$ROOT/bin/cocn.js" 测试.co

# eval
cd "$ROOT/src"
PWD="$PKG" COCN_TARGET="$PKG/测试.co" COCN_BACKEND=eval \
  node "$ROOT/bin/引导器" 解释器.co

# vm
```

## 六、三通道门禁

三通道不是“三个可选后端”，而是同一语义契约的三份实现：

| 通道 | 实现 | 作用 |
|------|------|------|
| native | C 启动器 + 直接机器码 ELF | 默认快路径，覆盖可安全直译子集 |
| eval | `src/求值器.co` 树遍历 | 原生不支持时兜底；语义对照 |
| vm | `src/虚拟机.co` 字节码 | 第二兜底；与 eval 互相校验 |

规则：

1. 改标准库、求值器、语法分析器后，至少跑语言套件相关用例；能跑全量就跑全量。
2. 改示例包后，必须跑该包 native/eval/vm 三次，stdout 逐字节一致。
3. 新增包必须通过清单校验、三通道验证，并尽量完成 `publish → install → 导入 → 运行` 闭环。
4. 原生后端不支持某写法时可以回退，但**不允许输出错误结果**；回退行为本身也要保持 stdout 一致。
5. 超时不是通过标准。`cocn-math` 在 Termux 上每通道约 65–75s，默认 60s 会误报；用 `COCN_VERIFY_TIMEOUT` 放宽后再判定。

当前基线：

- 语言套件：Termux/aarch64 上 eval 37/37、vm 37/37（2026-10-19 实测）；native 直编译通道待 x86 CI 复核。
- 首批包：**19 个**（2026-10-19 实测 **19/19 三通道一致**，逐包字节级一致）。逐包用例数：`cocn-result` 20/20、`cocn-math` 16/16、`cocn-fs` 15/15、`cocn-hash` 14/14、`cocn-semver` 12/12、`cocn-path` 12/12、`cocn-encoding` 9/9、`cocn-text` 8/8、`cocn-json` 5/5、`cocn-regex` 5/5、`cocn-rand` 5/5、`cocn-cli` 3/3、`cocn-config` 3/3、`cocn-url` 3/3、`cocn-hello` 2/2。
- 超时：`cocn-math` 在 Termux 上每通道约 65–75s，默认 60s 会误报；用 `COCN_VERIFY_TIMEOUT=300000` 放宽后通过。

## 七、新增包流程

1. 用 `cocn new <包名>` 生成脚手架，或复制 `示例包/cocn-fs/` 的 `co.toml` + `库.co` + `测试.co`。
   脚手架产出 `co.toml / 库.co / 测试.co / 程序.co` 四个文件，
   `程序.co` 直接演示库里的能力（CI 的「包演示冒烟」门禁会逐包跑它）。
2. 包名必须为 ASCII：`^[a-zA-Z0-9][a-zA-Z0-9_-]*$`。
3. `co.toml` 必填：`name`、`version`、`description`、`license`、`repository`、`lib`；可执行包再加 `main`。
4. 只写 `.co` 源码和 `co.toml`，不要新增 `README.md`、`docs/API.md` 或其他 `.md`。
5. API 说明写进源码 `#` 注释；需要生成时运行 `cocn doc`，输出为 `docs/API.txt`。
6. 测试写在 `测试.co`，用 `测试用例(...)` / `运行所有测试()`。
7. 跑三通道；跑清单校验；需要发布时再跑注册表闭环。
8. **每个包都要有 `程序.co`**：`co.toml` 的 `main = "程序.co"` 是清单与文件的一致性约定，
   `工具/生态/规范.js` 的 `校验入口` 现在会检查「声明的 lib/main 文件必须存在」。
   （本轮之前 19 个包都声明了不存在的 `程序.co`，直到加了这条校验才暴露出来。）
   `程序.co` 写成该包能力的最小可运行演示，兼作冒烟测试。
9. **命名规范**：包内函数名要带领域前缀，避免与标准库同名/近名造成遮蔽与混淆。
   - 标准库已有 `文件名` / `扩展名` / `目录名` / `路径拼接`（其中 `路径拼接` 是**列表拼接**、1 参，与直觉的 2 参路径拼接不同）。
   - 因此 `cocn-path` 的 API 统一用 `路径` 前缀：`路径连接` / `路径文件名` / `路径扩展名` / `路径规范化` / `路径组件` / `路径父目录` / `路径换扩展名` / `路径是绝对` / `路径绝对化` / `路径相对化` / `路径是子路径` / `路径共同前缀` / `路径有共同前缀` / `路径匹配通配` / `路径匹配任意` / `路径拆解`。
   - 经验法则：函数名 ≤ 3 个字时容易撞车，宁可长一点也要能自解释。
10. **API 要符合直觉**：包对外函数应能接受「用户最可能传的类型」。
    - `cocn-collections` 的 `并集/交集/差集/大小/转列表` 现在**列表与集合字典都收**（列表先归一为集合字典）。
    - 判断类型用 `类型(x) == "列表"`，**不要写 `x["类型"]`**——列表用字符串下标会报「下标必须是数字」。
11. 不手工改 `package.json` 的包数量描述以外的发布字段；版本号、description 必须与当前里程碑一致。

### 写包时最常踩的「标准库导出范围」速查（2026-10-19 实测）

`导入 "标准库"` 只导出 `src/标准库.co` 的顶层函数；`src/库/*.co`（字符串/列表/字典/数据结构/算法/文件系统/编码/加密/日期时间/系统）**必须显式 `导入 "库/xxx"`** 才可见。实测对照：

| 需要的能力 | 标准库直接可用 | 需 `导入 "库/xxx"` | 宿主内置（永远可用） |
|-----------|----------------|---------------------|---------------------|
| 字符串 | `查找` `截取` `替换` `分割` `去空白` `大写` `小写` `开头是` `结尾是` `包含` `去前缀` `去后缀` | `连接列表` `替换全部` `分割首` `分割后缀` `格式化` `模板填充` `Base64编码` `URL编码` | `码转字符` `字符码` `字节列表` `字节转文本` |
| 列表 | `追加` `插入` `删除` `移除` `弹出` `清空` `复制` `索引` `计数` `排序` `反转` `映射` `过滤` `归约` `切片` | `去重` `窗口` `累积` `并集` `交集` `差集` `子集` `超集` | `连接`（列表+分隔符） |
| 集合/字典 | `新建集合` `集合添加` `集合包含` `集合并集` `集合交集` `集合差集` `集合大小` `集合转列表` `频次` `键` `值` | —— | —— |
| 文件系统 | `文件名` `扩展名` `目录名` `路径拼接`（**1 参，列表拼接**） | `读文件` `写文件` `删除目录` `遍历目录` `创建目录` | `读文件` `写文件` `文件存在` `执行命令` `退出码` `环境变量` |
| 编码 | —— | `Base64编码` `Hex编码` `URL编码` `CSV解析` `CSV序列化` `RLE压缩` | —— |
| 字符/码 | `从ASCII`（标准库内部在用，但顶层并未定义——别指望可用） | —— | `码转字符` `字符码` |

写包时最容易踩的三件事：

1. `转整数()` 不能吃字母（`转整数("a")` 报类型错误）；字符与码互转一律用 `字符码()` / `码转字符()`。
2. `类型(x) == "列表"` 判断类型，**不要写 `x["类型"]`**（列表用字符串下标报「下标必须是数字」）。
3. 标准库不导出 `替换全部`，但导出 `替换`；要「全部替换」自己写（见 `cocn-encoding` 的 `全替换`）。
4. **同名函数：后导入者胜**。同时 `导入 "库/编码"` 与 `导入 "库"`（本包）时，后者覆盖前者——实测 `CSV解析` 最终走本包的 RFC4180 实现（更完整）。这个顺序依赖是既定行为，换包时按「后导入覆盖」预期即可。

## 八、coCN 编码坑（写代码前必读）

1. 变量声明用 `让`；交换临时变量不要写类型标注。
2. 函数名/参数名不能与类型关键字冲突：`整数`、`浮点`、`布尔`、`列表`、`匹配`、`默认` 等；约定 `列表` → `表`，`默认` → `缺省`。
3. 字典缺键返回 `空`；`空` 是 null，不是空串。判空用 `== 空`。
4. `截取(文本, 起点, 长度)`：**宿主 C 里第三参是长度**（`截取("abcdef",1,3)=="bcd"`）；但**标准库 `库/字符串.co` 的 `截取` 包装的是 `切片`，第三参是止点**（`截取("abcdef",1,3)=="bc"`）。同一函数名两套语义：标准库 `文件系统.co` 的 `文件名()` 按**长度**写，包内代码统一按**长度**写并加注释，别混用（2026-10-19 实测）。
5. 内置 `查找` 只支持 2 参；第三参（起始下标）会被忽略。
6. `对于` 循环内修改循环变量不会推进计数器；跳步用 `当` + 手动索引。
7. 不要包装内置 `包含` / `反转`，否则可能无限递归。
8. `现在()` 返回浮点；需要整数时间戳用 `转整数(现在())`。
9. 宿主级 I/O 错误不一定能被 `尝试/捕获` 拦住；文件操作坚持“先检查后操作”。
10. 内置 `目录存在` 不可靠；用 `执行命令("test -d '路径'"); 退出码()==0`。
11. 无默认参数：函数必须传满所有参数，除非标准库函数自己声明了默认值。
12. 多行匿名函数不要直接放在第一个参数位置；先赋值给变量再传。
13. 整数除法自动转浮点：`15/10 = 1.5`；要整数商用 `向下取整`。
14. 导入相对模块优先看 `环境变量("PWD")`；跑包测试必须设 `PWD=<包目录>`。
15. 包名必须 ASCII：`^[a-zA-Z0-9][a-zA-Z0-9_-]*$`。
16. 原生 AOT 不支持匿名函数：含 `测试用例(..., 函数() ... 结束)` 的包会回退解释器；三通道仍以 stdout 一致为准。
17. 临时文件一律优先 `TMPDIR`，不要写死 `/tmp`。
18. `npm pack/publish` 只发 `package.json` 的 `files` 白名单；改打包内容要同步 `files`。
19. `cocn publish` 入口是 `bin/cocn.js`（或安装后的 `cocn`），不是 `工具/生态/cli.js`；直接跑 `node cli.js publish` 不会执行。
20. 宿主报错坐标来自 C 启动器；改词法/语法的行列逻辑时，先跑 `测试/坐标对照.sh`，不要凭感觉改。
21. 位运算优先级低于比较/算术，混合表达式必须加括号。
22. 32 位无符号哈希取模不要依赖浮点；用 16 位拆分乘法，避免超过 2^53 丢低位。
23. **标准库只导出常用函数**：`连接`（列表+分隔符）、`分割`、`追加`、`弹出` 是宿主内置；`连接列表`、`切片` 等在 `库/字符串.co` / `库/列表.co`，需 `导入 "库/字符串"` 才可见。标准库自带 `文件名` / `扩展名` / `目录名` / `路径拼接`（简易切分版，不处理 `.`/`..`）。
24. **函数名不能以“不是/是否”这类中文疑问词开头**：`不是分隔符(...)` 会被解析成未定义名字，报「未知内置函数」。否定一律写 `非 条件(...)`。
25. 单行 `如果 条件 则 语句` 后**不能另起一行写 `结束`**（报「多余的 '结束'」）；多行分支必须写成 `如果 条件 则` + 缩进体 + `结束`。
26. 否定用关键字 `非`，不是 `不是`；`且` / `或` 优先级低于比较，混用时加括号。
27. **单行 `如果 条件 返回 X` 的 body 会延伸到下一条语句**：写「if 提前返回」时，后面紧跟的那条就是它的 body。若紧跟的是另一条 `返回`，后者会被吞进 if，导致函数在某些路径上无返回值（报「期望 整数，得到 字符串」这类怪异类型错误）。要两条 return 就写多行 `如果 … 则` + `结束`。
28. `转整数()` 不能直接吃字母（`转整数("a")` 报类型错误）；字符与码互转用宿主内置 `字符码(字符)` / `码转字符(码)`。标准库**不导出** `从ASCII`、`替换全部`（它们在 `库/字符串.co`），包内需要就自带实现。
29. 声明类型要与实际返回值一致：`整数 x = 截取(...)` 会报类型错误（`截取` 返回字符串）。写完先跑一次，看真实报错行号。

## 九、npm 发布形态（对标 deno / bun / node）

语言类 npm 包的通行做法是「主包 + 平台专属子包」，不是把二进制塞进主包：

| 包 | 做法 |
|----|------|
| deno | 主包无二进制；optionalDependencies 引 `@deno/linux-arm64-glibc` 等 6 个平台包；子包只带 os/cpu 约束 + 二进制 |
| bun | 同上，13 个 `@oven/bun-*` 平台包（含 musl / android 变体） |
| node | `preinstall` + `node-bin-setup`，按平台拉对应架构二进制 |

coCN 现在采用同一形态（0.1.31 起）：

- 平台子包：`@yeyelailou/cocn-linux-x64`、`@yeyelailou/cocn-linux-arm64`（各带 os/cpu 约束 + 引导二进制），由 `工具/发布/构建平台包.js` 生成。
- 主包：`optionalDependencies` 引用平台子包，npm 只装与本机匹配的那个；主包自身不再携带任何平台二进制。
- `bin/cocn.js` 的 `找引导器()` 按「COCN_BOOTSTRAP → 平台子包 → 主包」顺序查找，覆盖 npm 扁平化与嵌套两种 node_modules 布局（两种都实测命中）。
- 好处：装完即用，**不依赖 postinstall 联网下载**，也不依赖本机构建环境；架构不会再错配。

给平台子包打包时的硬规则：

1. 二进制架构必须与子包匹配（构建脚本按 ELF 魔数 + e_machine 校验，x86 产物塞进 arm64 子包会被当场拦下）。
2. 子包版本号必须与主包的 optionalDependencies 引用一致，且**先发子包再发主包**。
3. `bin` 字段指向 JS 入口而不是平台二进制（deno/bun 都是这样），否则 Windows 与非 x86 平台的 npm shim 会失效。

## 十、让更多平台认识 coCN（2026-10-20 整理）

### 现状：为什么 Gitee 认不出 coCN

Gitee / GitHub / VS Code 等平台都靠 **Linguist** 的语言表按**扩展名**识别语言。Linguist 的表里没有 coCN，`.co` 又与 Pascal 的老扩展名撞车，于是 coCN 源码全被归进「其他」——仓库语言统计不对、语法高亮缺失、代码搜索不认。

`.gitattributes` 只能把 `.co` 标成「可识别文本」，**不能凭空造一门语言**（`linguist-language=` 只能指向 Linguist 已知的语言；写 `Pascal` 更糟，会把 coCN 展示成 Pascal）。

### 通道能力差异（宿主 C vs 自举层，2026-10-19 实测）

宿主 C（`bin/引导器`，语义真值参照）与 coCN 自举层的能力并不完全等价，以下是实测差异，**不要对外承诺宿主通道支持这些**：

| 能力 | 宿主 C 通道 | 解释器通道（eval/vm） |
|------|------------|--------------------|
| `导入 "标准库"` | **不支持**：标准库第 434 行「字典成员 = 函数字面量」宿主解析器不接受，报「语法错误 (第434行,26列): 意外的符号 '函数'」 | 支持 |
| `导入 "<包名>"` 注册表回退 | **不支持**：宿主只 `fopen(相对路径)`，不查 `~/.cocn/registry` | 支持（`src/求值器.co` 的执行导入回退分支） |
| `导入 "/绝对路径.co"` | 支持 | 支持 |

结论：包生态（`cocn install` 后 `导入 "<包名>"`）目前只在解释器通道可用；宿主 C 通道只适合不依赖标准库与包的单文件程序。宿主源码 `co.c` 在远端历史（`git show 3038e46:co.c`）；按「只保留 .co 自举源码」的仓库纪律，宿主 C 不纳入本仓库，这两条差异记为已知边界。

## 十三、性能与边界（结论）

### 13.0 自解释器优化成果（0.1.39，2026-10-22）

两条兜底通道（eval 树遍历 / vm 字节码）都做了系统性优化，**语义逐字节不变**：

| 通道 | 基准 | 优化前 | 优化后 | 加速 |
|------|------|--------|--------|------|
| eval | fib(22) 递归 | 30995 ms | **20729 ms** | **1.49×** |
| eval | 100 万次累加 | 175533 ms | **81787 ms** | **2.15×** |
| vm | fib(22) 递归 | 24999 ms | **7826 ms** | **3.19×** |
| vm | 100 万次累加 | 922206 ms | **94746 ms** | **9.73×** |

（fib(22) 的数字来自同机交错 A/B（原始版本 vs 优化后，各测 2 次取最小值）；
100 万次累加的「优化前」是本轮开工时同机测得的基线，「优化后」为优化完成后同机复测，
机器负载会造成 ±30% 浮动，量级结论不受影响。

**循环类负载收益远大于递归**（vm 9.73× vs 3.19×），因为循环指令融合把
「一轮循环 11 条指令」压到 3 条控制指令 —— 这条路径上的指令条数直接决定耗时。）

**优化后 vm 通道已快过 eval 通道**（7.8s vs 20.7s）——原先 vm 是 eval 的 3~5 倍慢，
这与「字节码虚拟机天然比树遍历快」的常识一致，之前是实现层面的问题。

**优化前先测量，找对瓶颈**（这一步比优化本身更关键）：

- 宿主 C 的 `env_get` 是「作用域链 + 每层线性 strcmp」，**不是 O(1)**：
  每减少一次 coCN 级函数调用、一次宿主内置调用、一层 if 分派，
  就等于砍掉一次作用域链遍历。
- 实测口径：1 次 coCN 函数调用 ≈ 1µs；每执行 1 条【让】≈ +1µs；
  宿主内置调用（类型/包含/长度）要扫完整条链 + 求值器模块环境(186 项) + 根环境，
  约 600~1000 次名字比较。
- 于是优化方向明确为：**减少 coCN 级操作数**，而不是微调算法。

eval 通道（`src/求值器.co`）主要改动：

1. 分派链按频次重排（`求值` 14 段、`执行语句` 16 段、`求值二元` 的算术/比较分派）。
2. `求值二元` 类型只算一次（原来每侧算两遍），且整数 `+ - *` 早退到闸门前。
3. `调用用户函数` 在**函数定义时**把形参标注规范化成表 —— 原来每个形参每次调用
   都要付 1 次 `类型()` + 1 次 `长度()`。
4. 求值器私有的三个全局（求值深度/深度上限/当前返回类型）合成一个列表，
   `执行块` 每次省 3 次全局读写。
5. `是异常`/`是控制`/`是异常或控制` 去掉多余的 `为整数()` 包装；
   热点位置就地展开异常判定（`类型(x)=="字典" 且 包含(x,"__异常__")`）。
6. `层声明` 的大小判定用 `长度(末块)` 而非 `长度(键(末块))`（后者要新建键列表再拷贝）。

vm 通道（`src/虚拟机.co`）主要改动：

1. 帧从字典改成**列表**（原来每条指令要 6~8 次字典取值）。
2. 热路径状态「引用化 + 本地化」：栈/帧栈/异常标志在 `v_执行` 里取一次引用，
   之后全是下标操作（原来每条指令读 4~5 次全局）。
3. **操作码比较改用整数字面量**（原来每次比较要去读模块级全局 `OP_xxx`）。
4. 操作数栈加深度计数（`v_栈顶`/`v_弹出`/`长度(v_栈)` 三个调用换成一个下标）。
5. **循环指令融合**：`OP_循环条件` 改为只跑一次的初检，新增 `OP_循环推进`
   把「步长更新 + 续判条件」合成一条 —— 一轮循环从 11 条指令降到 3 条控制指令。
6. 二元运算与跳转的「就地快路」（整数与数值比较、加减乘、布尔真值），
   其余一律回落到原函数，报错文案与坐标不变。

**验证方式（这三条必须都做，缺一不可）**：

1. 语言套件 37 个，eval 与 vm 通道各 37/37 通过；
2. **双通道逐字节对照**：100 个程序（测试/*.co + 测试/坐标用例/*.co），
   eval 与 vm 的 stdout+stderr+退出码**逐字节一致**（100/100）；
3. 包门禁 19 个包 × 三通道逐字节一致（19/19）。

第 2 条尤其重要：vm 通道的优化过程中，双通道对照当场抓到过一个真 bug
（编译期「有没有形参标注要复查」的标志键写错，导致 `函数 f(整数 a)` 传字符串时
vm 通道不报错而 eval 报「类型错误（函数参数）」）。
**建议把双通道对照固化进 CI**（脚本见 `$HOME/cocnwork/dual.sh` 的形态：
逐程序跑两通道再 cmp）。

### 13.1 七语言同题实测（2026-10-21，aarch64，同机同架构）

复现：`工具/语言对比/计测.sh 30`（构建与执行都在 `$HOME` 下，绕开 `/storage` 的 noexec）。
负载：埃氏筛 10000（素数 1229）+ 递归 fib(20)（6765）+ 3000 次中文拼接（19893），
**七种语言输出必须逐字节一致**，否则本次计测无效（脚本会打印「一致/不一致」）。

| 语言 | 平均(ms) | 最快(ms) | 输出校验 |
|------|---------|----------|---------|
| C (gcc -O2) | 14.89 | 7.51 | 一致 |
| Rust (rustc -O) | 16.33 | 7.77 | 一致 |
| Go 1.27 | 41.35 | 25.08 | 一致 |
| Python 3.14 | 52.99 | 34.29 | 一致 |
| **coCN（引导器/宿主 C）** | **81.43** | **65.34** | 一致 |
| Node 24 | 161.66 | 133.60 | 一致 |
| Java 17 | 165.78 | 134.92 | 一致 |

**读这张表必须先说清楚一件事**：coCN 在这里跑的是**引导器（宿主 C）**通道，
不是 coCN 自己的速度上限。coCN 有三条执行通道，速度差两个数量级：

| 通道 | 实现 | 本机(aarch64) fib(22) | x86 用户体验 |
|------|------|---------------------|-------------|
| 直接机器码 | JS 代码生成器吐静态 x86-64 ELF | **本机跑不了**（后端只出 x86-64） | **0.12s**（历史同机实测，约 C 的 1/5） |
| 引导器（宿主 C） | 宿主 C 解释器 | 0.09s | 有 x86-64 引导器，同样 0.09s |
| eval / vm（自举） | coCN 自己写的解释器 | 0.02s / 0.008s | 同左，回退路径用 |

所以「coCN 能不能超越 C 和 Rust」的答案分两层：
- **x86 用户走直接机器码**：0.81ms vs C 0.66ms、Rust 0.70ms（trio 混合负载）——
  同一量级，**已追平到 80~85%**，这是 coCN 的真实上限。
- **非 x86 平台（如本机 aarch64）**：只能走宿主 C 解释器，81ms vs C 14.89ms ——
  差 5 倍，**没有追平**。原因是直接机器码后端目前只产出 x86-64 ELF，
  没有 aarch64 目标。**这是下一件最该做的事**（见第 13.5 节）。

本轮（0.1.39）优化的是 **eval / vm 两条自举通道**（aarch64 用户的回退路径、
coCN 编译自己的自举路径、以及语言套件门禁都走它们）：eval 快 1.49×、vm 快 3.19×。

分解（扣掉启动：coCN 8ms、Python 38ms、Node 172ms）：

| 负载 | coCN 净耗时 | Python 净耗时 | 结论 |
|------|-------------|--------------|------|
| 递归 fib(20) | 33ms | 66ms | coCN 快 2 倍（宿主 C 是真编译到字节码的解释器，比 CPython 快） |
| 埃氏筛 10000 | 40ms | 11ms | **coCN 慢 3.6 倍**（列表索引写 + 循环变量作用域查找） |
| 3000 次字符串拼接 | 24ms | 19ms | 基本持平 |

固定开销：coCN 引导器空程序 **8ms**（Python 38ms、Node 172ms）——启动成本是优势。

**结论要诚实说**：在 aarch64 上用宿主 C 跑，coCN 落在 Python 与 Node 之间；
在 x86 上用户走的是【直接机器码】通道（静态 ELF、无解释器），速度与 C/Rust 同档
（历史同机实测：coCN 0.81ms vs C 0.66ms、Rust 0.70ms）。
「同机同架构」这个前提不成立时不要把两边的数字放一起比。

### 13.2 与 Rust 的语义差异（必须写进对外说明）

| 语义 | coCN | Rust | 备注 |
|------|------|------|------|
| 整数除法 | `7 // 2 = 3`、`-7 // 2 = **-4**`（向下取整） | `-7 / 2 = -3`（向零截断） | **负数除法结果不同**，跨语言移植时最容易踩 |
| 真除法 | `/` 产出浮点 | `/` 对整数也截断 | coCN 的 `/` 在整数上会得到浮点 |
| 布尔 | 一等类型（`类型(真)=="布尔"`），与整数不互通 | 无独立布尔类型 | coCN 更严格，跨语言移植需显式转换 |
| 字符串长度 | 按【字符】计（UTF-8 码点） | `len()` 按字节，`.chars().count()` 按字符 | 中文场景需注意 |

| 能力 | 直接机器码 | 备注 |
|------|-----------|------|
| 整数运算/比较/逻辑 | ✓ | 含 `//` `%` |
| 字符串拼接/比较/长度 | ✓ | |
| 列表字面量/下标读写/长度 | ✓ | 元素限整数（无类型标签） |
| 函数/递归/循环 | ✓ | |

### 13.4 下一件最该做的事：直接机器码后端的 aarch64 目标

现状：直接机器码后端（`工具/原生编译器/机器码生成器.js`）**只产出 x86-64 ELF**。
后果：
- x86 用户拿到 0.81ms 级速度（与 C/Rust 同档）；
- **aarch64 / ARM64 用户拿不到这条路径** —— 只能走宿主 C 解释器（81ms，比 C 慢 5 倍）。

要做 aarch64 目标，需要在代码生成器里加一层「目标架构」抽象：

| 需要改的地方 | x86-64 现状 | aarch64 需要 |
|-------------|-----------|-------------|
| 整数寄存器 | rax/rcx/rdx/rsp/rbp… | x0~x30（30 个通用寄存器，参数走 x0~x7） |
| 栈帧与对齐 | 16 字节对齐、rbp 帧指针 | 16 字节对齐、fp(x29)/lr(x30) 链接寄存器 |
| 整数运算 | mov/add/sub/imul/idiv/cqo | add/sub/mul(可省)/sdiv/msub |
| 比较与分支 | cmp/setcc/jcc | cmp/csel/cbz/cbnz/b.cond |
| 调用与返回 | call/ret + 栈对齐 | bl/ret（lr 自动保存） |
| 浮点 | SSE2（movsd/addsd/…，要处理 xmm 传参） | **更简单**：标量浮点直接用 d0~d7，无 SSE 变数 |
| 地址大立即数 | movabs（10 字节） | movz/movk 组合（16 字节） |

**相对好消息**：aarch64 的浮点与调用约定比 x86-64 简单（标量浮点寄存器、
参数寄存器传递、无需 red zone、无方向标志），所以这条路的净工作量比直觉小。

验收标准（照 13.1 的口径）：
1. `工具/原生编译器/机器码生成器.js` 支持 `--目标 aarch64`，产出可在本机直接执行的 ELF；
2. 与宿主 C 通道**逐字节一致**（输出、异常消息与坐标）；
3. 七语言同题计测里 coCN 走 aarch64 直接机器码通道，与本机 C/Rust **同机同架构**比较。

预计工作量：代码生成器按「后端无关的 IR + 目标相关指令选择」重构，
保守估计 2~3 天（含验证）。这是达成「非 x86 平台也追平 C/Rust」的**唯一路径**。

### 13.4b 原生后端的字典与浮点：可执行的设计方案（0.1.39 记录，下一版实施）

现状：直接机器码后端支持整数/字符串/列表/函数/循环，**不支持字典与浮点**。
后果：用了字典或浮点的程序回退到引导器（宿主 C 解释器），
在 x86 上比直接机器码慢约两个数量级 —— 这是「看起来慢但说不清为什么」的
主要来源。`cocn --检查 程序.co` 现在能报出这个原因。

**关键约束（决定了方案形状）**：

- 列表元素在原生后端是**裸 8 字节槽、没有类型标签**，所以列表只允许整数元素
  （否则字符串元素会被当整数读出，静默算错）。
- 字典的**值**必须有类型信息：`d["a"]` 的结果种类在静态上不可知
  （同一个字典可能混放整数与字符串）。运行时已有 Box 机制
  （`rt_box_int/rt_box_str/rt_box_list/rt_box_dict`，`rt_dict_get` 返回 Box*），
  但**代码生成器目前完全没用 box**（槽位模型是「无标签裸值」）。
- 字典的**键**必须是字符串字面量：运行时 `rt_dict_set(d, k, v)` 的 k 是**指针**
  （字符串驻留地址），而字面量按内容去重（`strConst` 的 `strLabelMap`），
  所以同内容字面量地址一致 → 指针作键可靠；但**变量作键**时地址不同 → 必然匹配不上，
  必须编译期拒绝。

**建议的分三步走（每步都可独立发布、且必须 native 与 vm 逐字节一致）**：

第 1 步 · 字典（只支持同质整数值 + 字符串字面量键）
1. 槽位模型加一个「带标签的槽」变体：给每个槽加 1 字节 tag
   （0=裸整数、1=字符串指针、2=列表指针、3=字典指针），
   即槽宽从 8 字节变 16 字节（值 + tag）。这是**破坏性布局变更**，
   要求生成器与运行时**同一次改动**里一起改（否则会读到错位的 tag）。
2. 字典字面量：`rt_dict_create` → 逐键 `rt_dict_set(d, 字面量地址, rt_box_int(值))`。
3. 字典下标读：`rt_dict_get(d, 字面量地址)` → 得 Box* → 按 tag 解箱
   （`rt_unbox_int` / `rt_box_unbox_ptr`），**读取时按 tag 分派**，
   不能静态假定是整数。
4. 字典下标写：先装箱再 `rt_dict_set`。
5. 变量作键、非整数值、字典套字典：**编译期拒绝**（回退解释器），理由写进报错文案。
6. 验收：native 产物与 vm 通道的 stdout+stderr+退出码逐字节一致；
   再用 `测试/坐标用例` 那批程序做双通道对照。

第 2 步 · 浮点
- 浮点不能复用整数槽（8 字节里放 double 与放 long 的解释方式不同），
  需要给槽再加一个「这是浮点」标记，或约定「标注为 浮点 的变量一律 double 槽」。
- 运算走 SSE2（`movsd/addsd/mulsd/…`）；比较要用 `ucomisd` + 无分支写法
  （`cmov` 不存在于 x86-64 的常用集合里，得用 `setcc` + `movzx`）。
- 打印走已有的 `rt_print_double` / `rt_double_to_str`。
- 浮点列表/字典元素同样受「值要有类型标签」约束 —— 依赖第 1 步的 tag 机制。
- 验收同上；另外要特别测**除法、负数、精度边界**（0.1/0.3 这类）。

第 3 步 · 真除法 `/`
- 产出浮点，所以依赖第 2 步；`//` 已是整数向下取整，无需改。

**顺序很重要**：第 1 步的槽位布局变更是破坏性的，会牵动生成器里所有
「写槽/读槽」的地方（`allocVar`/`storeToSlot`/`genIndex`/函数调用传参/返回）。
所以第 1 步必须一次做完并全量验证，不能拆成「先改一半」——
半套标签机制比没有更危险（会出现「有的槽有 tag、有的没有」的混合布局）。

### 13.4c 已修复：`导入 "标准库"` 冷启动从约 18 秒降到约 2.5 秒（2026-10-28）

现象（修复前）：空程序只写一行 `导入 "标准库"`，冷启动到出现第一行输出约 **18~20 秒**
（同机 aarch64、vm 通道）。不导入任何模块的空程序约 0.25 秒。

根因（已定位，不是模块缓存缺失）：宿主 C 解释器的 UTF-8 字符层退化成了 O(n²)：
1. `源[p]` 每次下标都先 `utf8_strlen` 从头数长度做越界检查，再 `utf8_byte_offset`
   从头扫到 p；词法器逐字符扫描，整体 O(n²)。
2. `切片` 每取一个 token 都先 `utf8_strlen` 全文，再取两次偏移；同样 O(n²)。

标准库 63KB、约 3.8 万字符，于是「解析一遍」就要十几秒。

修法（`工具/引导器/co.c`）：
1. `utf8_byte_offset` 加单条 memo：同一字符串且下标不回退时从上次位置继续；
   字符串被 `free` 时立即失效（`val_free` 里清空），不会读到已释放内存，
   也不会把复用地址误判成同一串。
2. 字符串下标的**正索引**不再预算 `utf8_strlen`，只有负索引与越界报错才求长度。
3. `utf8_substr` 在非负起始/长度时不再先求全文长度。

实测（同机 aarch64、vm 通道、冷启动）：
- `导入 "标准库"`：17.9s → **2.5s**（约 7×）
- `导入 "语法分析器"`：22.4s → **2.5s**
- 10 个示例：每个 2.3~3.2s，10/10 通过

正确性：坐标用例 66/66 三通道一致；语言套件 eval 37/37、vm 37/37；
宿主新旧二进制对 66 个坐标用例逐字节零差异。

剩余：npm 平台子包里的预编译引导器需要按平台重新编译，用户才会受益；
构建命令见「构建与测试」。原方案「模块 AST 缓存」仍是后续可选项，
但根因修复后收益已不大。

### 13.5 其它结论

- 同题混合负载（x86 直接机器码）：coCN 原生约 **0.81ms**，C 约 0.66ms、Rust 约 0.70ms，处于同一量级；比 Go/Node/Python/Java 快一个数量级。
- 空程序启动约 **0.45ms**（x86 native 通道）；静态单段 ELF，无动态链接和运行时初始化。
- 重负载（1e7 累加、fib(30)）约为 C 的 **4–5 倍**，这是无寄存器分配架构的诚实代价。
- eval / vm 是兜底通道，速度远慢于原生，但保证“能跑且结果正确”；原生只覆盖安全子集。
- 基准代码必须能在【所有通道】跑：花括号糖（函数 体 { … }）只有自举解释器与原生前端支持，
  宿主 C 引导器不支持 —— 基准若用了它，测出来的就是「哪条通道能跑这段语法」，
  而不是语言速度。`工具/语言对比/bench.co` 因此改为缩进块写法。
