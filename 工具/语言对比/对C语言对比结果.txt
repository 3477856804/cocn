########## coCN 对 C 语言对比（实测，2026-10-25）##########
# 位置惯例：仓库只允许根目录一个开发准则.md，本文件按 工具/语言对比/
# 已有的 计测结果.txt 惯例写成 .txt，不新增 .md；基准源码与本文档同目录。
# 同目录源码：对C语言_斐波那契.co/.c、对C语言_累加.co/.c、
# 对C语言_排序.co/.c、对C语言_拼接.co/.c、对C语言_斐波那契20.co。

== 结论先说 ==
- 原生通道本身是可信的：四个同题程序，coCN 原生 ELF 与 C 输出逐字节一致。
- 速度上 coCN 原生还没追平 C：递归/大循环这类计算密集型慢约 4~5 倍；
  列表操作慢约 1.5 倍；字符串拼接基本持平。差距在实现成熟度，不在路线。
- 产物上 coCN 占优：静态自包含 ELF 只有 2.8~3.6KB；C 静态版约 785KB，
  动态版约 16KB 但不是自包含（换机器要带系统 libc）。
- 真正的差距不在速度，在覆盖：原生后端今天只能编“整数/字符串/列表/
  函数/循环”这个子集；语言本身（解释器通道）宽得多，但系统编程能力
  （指针、手动内存、内联汇编、直接系统调用）仍缺失。
- 所以“替代 C”今天的诚实表述是：x86_64 上、原生子集范围内的程序，
  coCN 可以做到与 C 同题同输出、速度同量级、产物更小；超出子集的，
  只能走解释器（慢 1~3 个量级），或等后端扩覆盖（T2 级大工程）。

== 测试环境与口径 ==
- 机器：x86_64，2 核；gcc 13.3.0；node v24.22.1；coCN 0.1.39。
- coCN 原生：./bin/cocn.js --编译 程序.co 输出（静态 x86-64 ELF，无 gcc
  依赖），直接执行 ELF；先过 ./bin/cocn.js --检查 确认可走原生快路径。
- C：gcc -O2；另用 gcc -O2 -static 打静态版对照体积。
- 防优化折叠：C 版的规模参数（n、k 上限）全部来自命令行参数（运行期
  变量），防止 gcc 把累加循环折叠成闭式解；coCN 版用字面量（原生后端
  不做这类优化，累加 217ms+ 的耗时证实是真循环，不是折叠）。
- 计时：每项跑 5 次，取最小值/中位值，单位 ms；共享虚拟机、2 核，计时
  有噪声，最小值更接近真实执行成本。
- 正确性：stdout 与 stderr 分别用 cmp 逐字节比对，不只看“数字对不对”。

== 产物大小（字节，ls -l）==
程序        coCN 静态 ELF   C -O2 动态版   C -O2 -static 版
斐波那契    2909            16040          785344
累加        2823            16008          785312
排序        3578            16096          785320
拼接        3006            16288          785376
口径必须讲清楚，否则数字会骗人：
- coCN ELF 是静态自包含的（file：statically linked，无 section header
  的极小 ELF），只含整数/列表/字符串极简运行时，不含 libc，换机器直接跑。
- C 动态版约 16KB，但不是自包含：运行时依赖 /lib64/ld-linux 与系统
  libc，换 libc 大版本不同的机器可能跑不了；拿它跟 coCN 的静态 ELF
  直接比体积，是拿“不完整”比“完整”。
- 自包含对自包含：coCN 2.8~3.6KB vs C 静态版约 785KB（glibc 静态链接
  的臃肿），coCN 小两个量级——但这很大程度上是因为 coCN 运行时极简，
  不是因为代码生成更强；等 coCN 运行时长大，这个优势会缩小。
- 所以“coCN 产物更小”在自包含口径下成立，在动态口径下数字上也更小
  但可比性弱；不要只贴一个数字下结论。

== 解释器通道对照（fib(20)=6765，单次，含启动）==
通道              耗时      说明
coCN 原生 ELF     2ms       启动主导，计算本身不到 1ms
C (-O2)           4ms       同样启动主导，与原生 ELF 同量级
coCN 引导器（宿主 C） 59ms  宿主 C 解释器，比原生慢约 30 倍
coCN vm（自举）   4832ms    比原生慢三个量级
coCN eval（自举） 13447ms   比原生慢近四个量级
另：vm/eval 跑 fib(25) 在 2 分钟内未出结果（主动终止，未继续等），
而原生 ELF 跑 fib(35) 只要 115ms——解释器通道只适合“能跑就行”的场景，
不能当成性能通道；回退是保正确性的设计，不是性能方案。

== 功能覆盖对比（两个层次，分开讲）==
== 第一层：coCN 语言本身（解释器通道）vs C ==
coCN 解释器通道有的（以 37 个语言套件 + src/库 + 19 个示例包为证）：
函数/递归、列表、字典、元组、字符串、匹配、OOP、枚举、异常、并发、
模块、文件系统、网络、日期时间、加密、算法、标准库扩充、REPL、包管理。
C 有而 coCN 解释器没有的（系统编程能力缺口）：
指针与手动内存管理、结构体/联合体/位域的底层布局控制、预处理器、
内联汇编、直接系统调用、独立编译链接与符号控制。
C 没有而 coCN 有的：中文语法、包管理与注册表、REPL、跨通道一致性
门禁（同一程序三通道逐字节比对）。
诚实结论：语言本身覆盖了应用层开发的大部分面，但系统编程那一面
（指针、内存布局、汇编、系统调用）是空白——“替代 C”在这一层还没开始。

== 第二层：coCN 原生后端目前能编什么（2026-10-25 实测）==
支持：整数运算/比较/逻辑（含 // %）、字符串拼接/比较/长度、列表字面量/
下标读写/长度（含负下标）、函数/递归/循环。
不支持（编译期拒绝，回退解释器；37 套 + 19 包 0 可编译皆属此类）：
匿名函数（24/37 套件主因）、结构体、枚举、尝试、并发、列表推导式、
浮点、字典、十六进制字面量、for-each 直接模式、真除法。
另：后端只产出 x86-64 ELF，无 aarch64 目标——非 x86 平台拿不到原生通道。
诚实结论：原生后端今天只覆盖语言的一个子集；写程序要先过 --检查
确认能否走原生，不能默认“coCN 程序 = 原生速度”。

== 开发体验对比（各写实在话）==
- 语法：coCN 关键字与标识符可用中文（函数/如果/返回/当/对于/输出），
  对中文使用者入门门槛低；代价是与英文技术资料、编辑器生态、搜索习惯
  不兼容，中英混写时风格难统一。
- 工具链：cocn 一个命令覆盖运行/编译/检查/包管理（15 个子命令）；
  gcc 只管编译链接，构建要另配 make/CMake。但 cocn 需要 node + 仓库
  （或 npm 平台包），gcc 单机可装、离线可用。
- 构建步骤：cocn --编译 一步出静态 ELF，不写 Makefile、不依赖目标机
  libc 版本；C 默认动态链接，换机器要带 .so，静态则体积大（实测 785KB）。
- 报错信息：coCN 报错是中文带行号，例如“语法错误 (第6行): 如果 块缺少
  结束，得到 ''”；但尾巴常跟一句“断言失败: 语法分析失败”，读起来像
  内部断言而非用户诊断。gcc 报错是英文，但精确到列、有 ^ 指示与补分号
  提示，几十年打磨的提示质量目前仍高于 coCN。
- --检查 是 coCN 更友好的一点：原生拒编时直接给出原因与改写建议，
  而不是让用户只看到“慢”却不知道慢在哪（本轮还修了一处误导性建议，
  见下一节）。
- 启动开销：空程序与极小程序上原生 ELF 与 C 同量级（fib(20) 都是 2~4ms，
  启动主导）；解释器通道则慢 1~3 个量级，见上表。

== 本轮顺带修复：--检查 的误导性建议 ==
- 现象：对解释器上完全合法、只是原生前端不支持的程序（例如匿名函数），
  ./bin/cocn.js --检查 原先建议“先修语法错误；语法不通过时任何通道都
  跑不了”——两句话都是错的：程序没有语法错误，解释器通道也能跑。
- 根因：原生前端在解析期就拒绝不支持的写法，抛出的也是“语法错误”，
  检查能力函数（工具/原生编译器/机器码生成器.js 的 检查能力）在解析失败
  分支里不区分“真语法错误”和“前端不支持”，统一给了修语法建议。
- 修复（仅改建议文案，不动解析器、不动代码生成器）：解析失败且错误信息
  含“暂不支持”时，改建议为“这是原生前端暂不支持的写法，不是语法错误；
  解释器通道能直接跑（结果一致，只是慢），改写成原生支持的写法即可走
  快路径”；真语法错误保留原建议。
- 验证：匿名函数程序给出新文案；真语法错误（括号不闭合）保留旧文案；
  四个基准程序仍报告可走原生；文件 node --check 通过；全量 eval/vm
  套件回归见下一节。
- 未动的地方：原因行里的“语法错误 (第 N 行)”仍是解析器原话（改它可能
  影响错误用例比对），以及报错尾巴的“断言失败”——这两处是文案打磨，
  不在本轮修。

== 全量 eval/vm 套件回归 ==
- 修复后在副本里跑全量语言套件（测试/套件三通道.sh bin/cocn "eval vm"）：
  37 套，eval 通过 37 / vm 通过 37，与修复前基线（37/37）一致，无回归。
- 脚本汇总里的 native 通过 0 / 三通道一致 0 是因为本轮只跑了 eval/vm
  两个通道（native 通道未传参），不是失败；上一轮原生门禁 29/29 的结论
  不受影响（本轮未改代码生成器，只改了 --检查 的建议文案）。

== 还剩的大缺口（按“替代 C”的目标排）==
1. 后端扩覆盖：匿名函数、结构体、枚举、尝试、并发、列表推导式、浮点、
   字典、十六进制字面量、for-each 直接模式、真除法——T2 级大工程，
   不是最小化修复能做的。
2. aarch64 目标：后端只出 x86-64 ELF，非 x86 平台拿不到原生通道。
3. 系统编程能力：指针、手动内存、内存布局控制、内联汇编、直接系统调用
   ——语言层面仍是空白。
4. 计算密集型性能：递归与大循环仍比 C 慢约 4~5 倍，需函数调用与循环
   生成优化。
5. 报错打磨：“断言失败”这类内部口径文案、以及原因行里把“不支持”说成
   “语法错误”的解析器口径，需要一轮统一梳理。

== 复现方法 ==
- 实验副本（不污染主克隆）：~/workspace/coCN-verify/vs-c（b2e957b 复制，
  仅在副本里 npm install 拿引导器、构建启动器）。
- coCN 原生：./bin/cocn.js --检查 程序.co；./bin/cocn.js --编译 程序.co 输出。
- C：gcc -O2 程序.c -o 程序（规模参数走命令行）；gcc -O2 -static 程序.c
  -o 程序_static 对照体积。
- 计时：date +%s%N 前后相减，每项 5 次取最小值/中位值；正确性用 cmp
  逐字节比对 stdout/stderr。
